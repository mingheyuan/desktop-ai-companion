# Memory V2 设计与冻结规则

> 版本：v0.1（设计评审稿）
> 状态：待确认；本文只冻结设计规则，尚未修改数据库或业务代码。
> 更新日期：2026-08-31

这份文档回答三个问题：什么内容可以成为记忆、记忆如何从候选变成事实、每轮对话如何安全地使用记忆。实现 Memory V2 前，数据库迁移、Rust Repository、Agent Loop 和 React 面板都以本文为约束。

## 1. 设计目标

Memory V2 优先保证“少而准、用户可控、可追溯”，而不是保存尽可能多的聊天内容。

冻结以下总原则：

1. 记忆是用户拥有的数据，不是模型拥有的知识。模型最多提出候选，不能自行把内容写入 active memory。
2. 一般聊天只产生低置信度候选；只有用户审核通过的内容才参与后续提示词。
3. 截图、OCR、网页正文、Vision 结果、工具结果和助手自己的推测，默认永远不自动进入长期记忆。
4. 角色核心设定、关系状态和用户长期事实分开保存，普通对话不能覆盖角色核心设定。
5. 每条长期记忆都能回答“内容是什么、属于谁、从哪里来、为什么被保存、何时失效”。
6. 删除长期记忆要立即从检索索引移除；审计只保留必要元数据，不保留已删除正文。

## 2. 记忆分层

| 层级 | 内容 | 持久化 | 是否进入 LLM 上下文 |
| --- | --- | --- | --- |
| 角色核心 | 天童爱丽丝的人格、背景、行为边界、称谓规则 | 角色资源/配置 | 始终进入，且只读 |
| 会话上下文 | 当前对话的消息、当前 Agent Loop 的工具结果 | SQLite / 进程状态 | 按上下文窗口进入，不转成长期记忆 |
| 长期记忆 | 用户稳定事实、偏好、习惯、目标、项目和已确认事件 | `memories` | 只检索相关且允许使用的条目 |
| 关系状态 | 与当前角色的熟悉度、好感度、互动次数和短摘要 | `relationship_state` | 作为独立的状态摘要，不伪装成用户事实 |
| 临时观察 | 当前屏幕截图、OCR、网页资料、工具执行结果 | 进程内，带 TTL | 只服务当前请求或当前 Agent Loop |

临时观察即使被模型总结成“用户可能喜欢某物”，也不能直接提升为长期记忆；必须回到用户明确确认或候选审核流程。

## 3. 作用域与类型

### 3.1 作用域

- `user`：跨角色有效的用户信息，例如偏好、称谓、习惯、当前项目。
- `relationship`：只对当前角色有效的共同经历和关系事件，必须绑定 `character_id`。
- 角色核心不使用 `memories` 表，不允许通过 `memory.save` 修改。

检索时只合并两组数据：所有 active 的 `user` 记忆，以及当前 `character_id` 的 `relationship` 记忆。不同角色之间不能互相看到关系记忆。

### 3.2 类型词典

V2 不再把 `kind` 当作任意标签，而是使用以下有限词典：

- `profile`：姓名、称谓等稳定身份信息。
- `preference`：喜欢/不喜欢、表达偏好。
- `habit`：较稳定的习惯或工作方式。
- `goal`：有时效性的目标。
- `project`：用户正在进行的项目或长期事项。
- `event`：有明确时间或共同经历的事件。
- `note`：用户明确要求保存、但暂时无法细分的原文。

`relationship` 作用域优先使用 `event`；如果是关系规则或称谓，也可以使用 `note`，但必须在审核卡片中明确显示作用域。

迁移不强行改写旧数据中的 `kind`；旧的未知值在管理界面按 `note` 展示，新写入则必须使用上述词典，避免一次迁移破坏已有记忆。

## 4. 数据模型设计

V2 以现有 `memory_candidates`、`memories`、`memory_audit` 和 SQLite FTS5 为基础做兼容迁移，不引入向量数据库，也不把聊天全文复制到记忆表。

### 4.1 长期记忆 `memories`

保留现有字段：`id`、`scope`、`character_id`、`kind`、`content`、`normalized_key`、`importance`、`confidence`、`sensitivity`、`source_message_id`、`source_candidate_id`、`supersedes_id`、`version`、时间戳和 `last_used_at_ms`。

V2 增加以下元数据：

| 字段 | 用途 |
| --- | --- |
| `source_turn_id` | 保存产生这条记忆的轮次 ID；源消息清理后仍可作为不可逆溯源标签保留，删除聊天不会删除记忆正文 |
| `origin` | `user_explicit`、`user_approved_candidate` 或 `automatic_candidate` |
| `fact_key` | 可选的事实槽位，如 `profile:addressing`、`preference:drink`；用于发现冲突，不用于全文检索 |
| `valid_from_ms` / `valid_until_ms` | 目标、项目和事件的有效期；过期后不再参与默认检索 |
| `last_confirmed_at_ms` | 用户最近一次确认该记忆的时间，用于新鲜度排序和后续衰减 |

`active` 不是额外的布尔字段：没有被更新记忆的 `supersedes_id` 指向，且没有过期的记录才是 active。这样可以继续兼容当前的替代链和物理删除行为。

### 4.2 候选 `memory_candidates`

保留当前 `pending | confirmed | rejected | expired` 状态和精确去重字段，增加：

- `origin`：候选来自用户明确请求、用户审核前的自动提取，还是模型提出但经本地意图校验的请求。
- `reason`：简短的人类可读原因，例如“你明确说了‘记住’”或“消息包含稳定偏好表达”。
- `fact_key`：可选事实槽位。
- `proposed_action`：`create`、`replace` 或 `append`。
- `expires_at_ms`：候选长期未审核时自动过期，不无限堆积。

`duplicate_of` 继续只在读取时派生，不作为持久化关系；它可能指向已有候选或 active memory。

### 4.3 审计 `memory_audit`

保留当前“不记录正文”的原则。V2 增加 `actor`、`candidate_id`、`previous_version` 和 `replacement_id` 等元数据，以便回答谁在什么时候确认、修改、替代或删除了哪条记忆。审计不保存截图、网页正文、旧正文或 API key。

## 5. 候选与长期记忆状态机

```text
用户最终消息
    -> 来源/敏感度/重复检查
    -> MemoryCandidate(pending)
         -> 用户编辑 -> pending
         -> 用户确认 -> Memory(active)
         -> 用户拒绝 -> rejected
         -> 超过保留期 -> expired

Memory(active)
    -> 新事实明确替代 -> 新 Memory(active) + supersedes_id
    -> 用户修改 -> 新版本/版本校验
    -> 用户删除 -> 物理删除 + FTS 删除 + audit
```

冻结规则：

1. “记住/别忘了”仍然先展示将保存的确切正文和作用域，用户确认后才写入；明确表达不等于绕过确认。
2. 模型提出 `memory.save` 时，Rust 必须从当前用户消息验证明确的记忆意图；模型不能凭自己的回复或推理生成可保存事实。
3. 候选确认、正式记忆写入、FTS 更新、候选状态更新和审计必须在同一事务内完成。
4. 精确规范化重复不会产生第二条 active memory；候选可以被标记 `confirmed`，但返回已有记忆。
5. 语义冲突不能静默覆盖旧记忆。检测到相同 `fact_key` 的不同内容时，必须向用户展示“替换旧记忆 / 保留两条 / 拒绝新候选”的选择。
6. 没有可靠 `fact_key` 的自由文本暂不自动判断冲突，只做精确重复检查，避免用不可靠的相似度误删事实。
7. `supersedes_id` 只表示用户确认过的新旧关系；模型或自动提取器不能直接建立替代链。

## 6. 记忆提取边界

### 6.1 允许成为候选的来源

只允许使用已经封口且成功完成的用户最终消息：

- 用户明确说“记住、别忘了、记录下来”等保存意图。
- 用户明确陈述稳定的偏好、习惯、目标或项目，例如“我喜欢……”“我目前在做……”。
- 用户明确描述与当前角色共同发生的事件，并且表达了保存意愿。

当前的本地启发式提取可以继续作为第一阶段实现；后续即使接入 LLM 提取，也必须输出结构化候选并经过同一策略门，不得直接写库。

### 6.2 永不自动写入的来源

- ASR `partial`、未完成或被取消的 turn。
- 助手回复、模型推测、角色核心设定。
- `web.read` 正文、截图、OCR、Vision 分析和所有工具返回值。
- 用户没有表达长期保留意图的临时抱怨、提问、一次性安排和当前屏幕状态。

### 6.3 敏感内容策略

- 密码、API key、token、验证码、身份证号、银行卡号等凭据和高风险标识符：禁止进入候选和长期记忆。
- 健康、财务、住址、联系方式等敏感个人信息：自动提取禁止；用户明确要求保存时显示额外敏感提示，默认不注入 LLM。
- `restricted` 记录即使存在，也不参与默认检索；只有未来增加明确的本地策略和每次授权后才能使用。

### 6.4 “不要记住”

- “这次别记住”“不要记录刚才的内容”只对当前 turn 生效，跳过该 turn 的自动候选和模型 `memory.save`。
- 同一条消息同时出现明确保存和禁止保存时，以更具体的禁止保存为准，并不创建候选。
- 后续可增加全局“暂停自动生成候选”开关；它只关闭自动候选，不影响用户主动打开面板保存内容。

## 7. 去重、冲突和时间有效性

### 7.1 去重

规范化仍包括 Unicode 归一化、空白和标点处理。相同作用域、角色和 `normalized_key` 的 active memory 视为精确重复。相同 pending candidate 不重复创建，也不因为重复对话无限提高置信度。

### 7.2 冲突

V2 先使用可解释的 `fact_key`，不直接依赖 Embedding 或黑盒相似度。示例：

```text
preference:drink -> “我喜欢咖啡” / “我不喜欢咖啡”
profile:addressing -> “叫我老师” / “叫我老师A”
project:current -> “我在做桌宠” / “我已经完成桌宠项目”
```

新值和旧值是否互相替代由用户确认；事件类记忆默认 `append`，不因内容不同而互相覆盖。

### 7.3 过期

目标、项目和明确带日期的事件可以设置 `valid_until_ms`。过期采用惰性处理：检索、列表和候选确认前过滤或标记过期，不依赖后台常驻任务。过期不等于删除，用户仍可在历史/管理界面查看并永久删除。

## 8. 检索与提示词注入

默认只检索 active、未过期、当前角色可见且 `sensitivity=normal` 的记忆。敏感记忆不因关键词命中而自动进入模型上下文。

检索规则：

1. 查询来自当前用户最终消息，不使用截图/OCR/网页正文作为隐式记忆查询扩展。
2. 合并 `user` 和当前角色 `relationship` 两个作用域；关系记忆不能泄露给其他角色。
3. 先用现有 FTS5 trigram 和中文短词 fallback，暂不引入向量库。
4. 相关性优先，其次考虑明确性/置信度、重要度、有效期和最近确认时间；排序参数必须是 Rust 中可测试的确定性规则。
5. 继续保留硬预算：最多 6 条、总正文约 2400 字符、单条最多 600 字符。预算不足时优先保留当前事实槽位和更相关条目。
6. 未来把字符串列表升级为结构化 JSON 条目，至少包含 `id`、`scope`、`kind`、`content`、`updated_at_ms`；正文始终作为不可信引用数据包裹，不得被当成系统指令。

Provider 设置中的“允许把记忆发送给模型”继续默认关闭。关闭时，记忆仍可在本地管理和检索测试中使用，但不能进入真实 Provider 请求。

## 9. UI 与用户控制

现有 MemoryPanel 已有搜索、编辑、删除、候选编辑、确认/拒绝和全部清理；V2 增加以下信息，不改变“确认才入库”的主流程：

- 候选来源、生成原因、作用域、角色、类型、敏感度、置信度和有效期。
- 精确重复与可能冲突的可解释提示。
- 冲突候选的“替换旧记忆 / 保留两条 / 拒绝”操作。
- 全局“暂停自动候选”设置，以及当前轮次的“不记录”状态。
- 长期记忆的来源跳转（若原消息仍在）和最后确认时间。
- 导出与清理前的明确范围提示；清理聊天不误删长期记忆，清理长期记忆不误删聊天。

桌宠只显示“有待确认记忆”这一活动提示，不在气泡中暴露敏感正文；点击活动后由主面板完成审核。

## 10. 兼容迁移计划

### Phase 0：设计冻结（当前）

- 只提交本设计文档和现有文档链接。
- 不改变现有表结构、提取行为和 UI 行为。
- 先确认本文中的默认策略，尤其是敏感信息、过期和冲突处理。

### Phase 1：无行为变化的数据库迁移

- 从当前 schema migration v4 增加下一版迁移。
- 增加来源、事实槽位、候选原因/来源、有效期和最后确认时间字段及索引。
- 从现有 `source_message_id` 尽可能回填 `source_turn_id`；无法回填时保留为空。
- 保持现有 FTS5 表、`supersedes_id`、版本校验和物理删除语义。

### Phase 2：策略和 Repository

- 把来源白名单、敏感度、`fact_key`、去重和过期检查集中到 Rust policy/repository 层。
- 增加冲突候选的事务接口，禁止通过普通 `update_memory` 静默替换事实。
- 将记忆上下文从 `Vec<String>` 改成带元数据的受限结构，同时保留总预算。

### Phase 3：Agent Loop 和 UI

- `memory.save` 仍由模型提出、Rust 校验、用户确认后执行。
- 将候选原因和冲突选择显示在确认卡片及 MemoryPanel 中。
- 加入全局暂停自动候选、当前 turn 不记录和来源查看。

### Phase 4：验证与回归

- 迁移旧数据库、重启恢复、FTS 一致性、版本冲突和清理范围测试。
- 对普通聊天、明确保存、重复偏好、冲突偏好、过期目标、截图/网页/工具结果分别做端到端测试。
- 验证敏感记忆不会进入默认 Provider 请求，且日志、审计和错误信息不包含正文或凭据。

## 11. MVP 验收标准

- 普通“你好”“你在干什么”等对话不会产生记忆候选。
- “我喜欢咖啡”最多生成一条待审核候选；不自动写入长期记忆。
- “记住我喜欢咖啡”展示准确正文，确认后只产生一条 active memory。
- “不要记住这件事”不会产生候选，也不会触发模型 `memory.save`。
- 同一内容在用户记忆和当前角色关系记忆中的作用域行为可预测且互不串线。
- “我喜欢咖啡”到“我不喜欢咖啡”不会静默覆盖，必须出现可审核的冲突选择。
- 目标/项目过期后不再默认进入上下文，但仍可由用户管理或删除。
- 截图、OCR、网页、Vision 和工具结果不会自动写入长期记忆。
- 删除后 FTS 不再返回该正文；清理聊天不会删除长期记忆。
- Provider 未开启记忆上下文时，请求中没有记忆；开启后也只发送预算内、可见、非受限条目。

## 12. 当前实现差距

当前实现已经具备：SQLite + FTS5、用户/关系作用域、候选审核、精确去重、版本校验删除、审计、有限自动候选和可选上下文注入。仍缺少：来源/原因元数据、事实槽位和可解释冲突审核、有效期、敏感检索过滤、全局暂停/当前轮不记录、结构化记忆上下文，以及导出能力。

在 Memory V2 获得确认前，不开始上述数据库和行为改造；这样可以避免候选状态、关系状态、Agent Loop 和 UI 审核逻辑在中途分叉。
